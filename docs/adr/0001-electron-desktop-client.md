# ADR 0001 — Electron Desktop client for Codex app-server

- Status: Accepted
- Date: 2026-10-14
- Scope: `desktop/` client and app-server v2 integration
- Target platforms: macOS, Linux, Windows
- Related issue: `#30`

## Summary

Build the self-developed Codex Desktop client as an **Electron + React + Vite** application that talks **only** to Codex `app-server` through the generated v2 JSON-RPC contract. Electron owns process management and native integration; React renders the UI; the app-server owns Codex business state, approvals, threads, and tool execution.

## Context

Codex already provides the backend contract the client needs:

- `codex app-server` supports `stdio://`, `unix://`, `ws://`, and `off` transports.
- `codex-rs/app-server-protocol` contains the v2 request, response, and notification types.
- `codex-rs/app-server-daemon` provides a managed local daemon lifecycle for local and remote clients.
- The repository already has a generated TypeScript schema under `codex-rs/app-server-protocol/schema/typescript`.
- The official Desktop app is external to this repository; `codex app` launches it.

The repository does **not** currently contain:

- an in-tree Desktop client,
- a reusable TypeScript app-server client package,
- Desktop packaging, signing, or update automation,
- an ADR record.

## Decision

Adopt the following architecture:

1. **Desktop shell:** Electron.
2. **Renderer:** React + Vite.
3. **Protocol:** generated TypeScript types from `codex-rs/app-server-protocol/schema/typescript`.
4. **Process boundary:** Electron main is the only layer that spawns or attaches to `codex app-server`.
5. **Business boundary:** Desktop never imports or calls `codex-core`, `codex-tui`, or any Rust crate directly. All business state and actions flow through app-server JSON-RPC.
6. **Security boundary:** approvals and external side effects remain owned by app-server. Desktop only displays requests and returns explicit user decisions.
7. **Recovery boundary:** durable state is reconstructed from `thread/list`, `thread/read`, and app-server events. Renderer memory is never treated as authoritative after a crash.
8. **Schema discipline:** generated protocol files are checked in and regenerated by script; manual edits are prohibited and fail CI.

## Protocol compatibility

- The client targets app-server **v2** and the checked-in generated TypeScript schema.
- Compatibility is enforced with the existing `initialize` response contract, strict generated-schema validation, and runtime rejection of malformed or unexpected v2 payloads.
- An app-server that fails `initialize`, returns an incompatible response, or emits payloads outside the generated v2 contract fails closed with an explicit error.
- The client does not silently degrade to an older protocol, bypass schema validation, or guess compatibility from a response shape.
- Exact protocol revision negotiation is **not** currently exposed by the Rust protocol and is therefore not part of this ADR.
- Regeneration is performed from `codex-rs/app-server-protocol/schema/typescript`; manual edits are forbidden and detected by CI.

## Why Electron instead of Tauri

Electron was selected because UI quality and cross-platform rendering consistency are higher-priority than minimizing binary size for this client. Electron ships a consistent Chromium runtime across macOS, Linux, and Windows. Tauri relies on platform-specific WebViews, which would require additional compatibility and visual-regression work, especially on Linux WebKitGTK.

This is a deliberate tradeoff, not a claim that Tauri is unsuitable for all products.

## Alternatives considered

| Option | Result |
|---|---|
| Electron + React | Chosen. Best rendering consistency and web tooling maturity. |
| Tauri + React | Rejected for this client because platform WebView variance increases UI risk. |
| Native per-platform UI | Rejected because three independent UI stacks would triple implementation and review cost. |
| Extend the TUI | Rejected because the TUI is a separate client surface and not a reusable desktop shell. |
| Embed a web view in the existing CLI | Rejected because it would couple product delivery to the CLI process and weaken the app-server boundary. |

## Scope

### In scope

- Electron main/preload/renderer structure.
- React UI foundation and design system.
- Generated TypeScript protocol package.
- App-server process manager and JSON-RPC client.
- Thread list, start, resume, and conversation stream.
- Approvals, diffs, and user input.
- Reconnect, crash, shutdown, and recovery.
- E2E and compatibility tests.
- Packaging, signing, and update safety.
- Managed daemon attachment in a later phase.

### Out of scope

- Rewriting `codex-core`.
- Creating a second TUI.
- Public remote-control exposure.
- Building an embedded IDE.
- Automatic approvals.
- Replacing the official Desktop app.
- Modifying the Rust app-server protocol in this ADR.

## Security and trust model

1. Electron main is the only process with Node and child-process authority.
2. Renderer code cannot import Node APIs directly.
3. Preload exposes only explicitly declared, typed methods.
4. Secrets never enter renderer state or `localStorage`.
5. Approval requests are answered exactly once.
6. No approval is inferred from crash recovery, reconnection, or stale UI state.
7. External side effects are allowed only after an explicit user approval response accepted by app-server.
8. Protocol schema drift fails closed.
9. Generated files cannot be hand-edited without failing CI.

## State machine invariants

### Connection

`Disconnected -> Starting -> Initializing -> Ready -> Reconnecting/ShuttingDown`

- Business requests are allowed only in `Ready`.
- A connection that leaves `Ready` must terminate pending requests deterministically.
- Reconnect starts with a fresh initialize handshake.

### Thread

`NotLoaded -> Loading -> Ready`

- A thread view binds to exactly one app-server thread ID.
- Loading cannot be skipped by optimistic renderer state.

### Turn

`Idle -> Starting -> Running -> Terminal`

- A terminal turn is not unconditionally overwritten by a late notification.
- The final state comes from app-server events or a successful durable read.

### Approval

`Pending -> Responded/Cancelled/Expired/Disconnected`

- No transition returns to `Pending`.
- A request can be answered only once.
- Crash recovery never replays an approval decision.

### Recovery

`Crashed/Disconnected -> Restoring -> Ready | Error`

- Recovery begins only after a fresh app-server connection reaches `Ready`.
- `Restoring` performs a durable reconciliation using `thread/list`, `thread/read`, and current app-server events.
- Renderer memory cannot promote a thread directly from `Crashed` to `Ready`.
- A late event from an old connection may refine state but cannot override a newer durable read.
- If reconciliation cannot complete, the state becomes `Error`, not an optimistic `Ready`.

## Failure, concurrency, and recovery requirements

The client must explicitly handle:

- malformed JSON-RPC frames,
- unknown methods,
- oversized `thread/resume` responses,
- request timeouts,
- server overload,
- shutdown admission rejection,
- app-server process exit,
- Electron main crash,
- renderer crash,
- reconnect during an active turn,
- multiple windows operating the same thread,
- late responses from an old connection,
- multiple simultaneous approval requests,
- external clients updating the same thread.

Recovery must use durable app-server state or a definite error. The client must not infer success from stale memory.

## Testing and acceptance contract

1. Unit tests cover protocol typing and state machines.
2. Integration tests run Electron main against a fake app-server.
3. E2E tests run Electron plus a real local app-server and mocked model.
4. CI runs Desktop lint, build, and tests.
5. Schema drift tests fail if generated TypeScript no longer matches the Rust schema fixtures.
6. Recovery tests kill the app-server process and assert deterministic UI state.
7. Approval tests assert that deny produces no external side effect and approve executes exactly once.

## Rollout and rollback

- Each capability lands behind an independent feature flag or bounded PR.
- Reverting a Desktop PR does not affect Rust business behavior.
- Approval UI may be hidden only while the client fails closed; it must never fall back to automatic approval.
- Packaging and public release are separate from this ADR and require explicit authorization.
